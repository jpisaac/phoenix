# Phoenix WHERE Optimizer Redesign [PHOENIX-6791](https://issues.apache.org/jira/browse/PHOENIX-6791)

Contributors: [Kadir Ozdemir](mailto:kozdemir@salesforce.com), [Tanuj Khurana](mailto:tkhurana@salesforce.com)  
Updated: Jan 19, 2023

This document lays out issues, complexities and inefficiencies with the WHERE optimizer in Phoenix and proposes a redesign to address them.

# Background

An HBase table can be viewed as a set of cells where each cell is identified by a key, which is composed of a row key, family name, column qualifier, and timestamp. A cell holds a value expressed using a byte array. So essentially, a cell is a key-value structure and HBase is a key-value store. A row is identified with a row key and is the set of cells with this row key. Rows in an HBase table are sorted by the row key of the table. 

Phoenix is a relational database with a SQL interface, and uses HBase as its backing store. Phoenix tables are backed by HBase tables, and the primary key of a Phoenix table maps to the row key of the underlying HBase table. One may consider Phoenix as a translator between JDBC API and HBase API. Although Phoenix is much more than a mere translator, this model is useful to understand how Phoenix works.

HBase tables are divided horizontally by row key range into regions called table regions. Table regions are assigned to the nodes in the cluster, called region servers, and these serve data for reads and writes. 

Phoenix does not simply translate a SQL query on a Phoenix table into a scan over the corresponding HBase table using HBase API. Instead, Phoenix typically generates a set of scans each of which is for a specific table region. These scans are then executed in parallel typically, or sequentially if the query requires sequential execution. It is the job of the **WHERE optimizer** to identify the table regions to be scanned for a given query to skip the table regions which are not required for this query. 

The WHERE optimizer in Phoenix derives the information about which row key ranges to be scanned from the primary key (PK) column expressions in a WHERE clause. A given table can include multiple PK columns. In this case, the row key of the table is an ordered composition of these columns. It should be noted that row key ranges can only be generated if the WHERE clause includes expressions for PK columns that can form row key prefixes. For example, if a Phoenix table has PK columns A, B, and C, the order of PK columns is A, B, and C and A is not included in the WHERE clause, then it is impossible to identify the row key ranges.

An HBase scan object has start and stop row key values and an HBase filter to be used by the region servers to filter rows. The start and stop key of a scan defines what is called in the code scan range. The derived row ranges are used to determine scan ranges. Also, the row ranges are used to further filter out the rows within a scan range using what is called **SkipScanFilter** in Phoenix. A SkipScanFilter is used to skip HBase rows using the derived key ranges. Phoenix SkipScanFilter is an HBase custom filter and uses the HBase seek functionally to seek from one row to another.

In the next sections, we will describe how this is done.

## Parser

The Antlr code that generates SQLParser for Phoenix has a factory of ParserNodeFactory. There is no formal parser node concept or the ParserNode class in Phoenix but there are various classes referred as parser nodes such as SelectStatement, TableNode, ParseNode, LimitNode etc and that are generated by ParserNodeFactory.

A SQL select statement is represented by a class called SelectStatement and the clauses within a select statement are represented by various classes generated by ParserNodeFactory. ParseNode is an abstract class that can have a list of child parse nodes. A ParseNode accepts a ParseNodeVisitor via its accept() method. Parser nodes can form a hierarchical structure (by having child nodes) and this structure is traversed with a ParseNodeVisitor. The hierarchical clauses in a SQL statement are represented by ParseNode objects and the compilers, statement rewriters, finders etc for these clauses are implemented by a ParseNodeVisitor. For example, the FROM clause of a select statement is represented by a TableNode which is not a ParseNode. However, the WHERE clause is represented by a ParseNode since it can have a tree structure. The WHERE compiler is implemented as a ParseNodeVisitor. 

## WHERE Compiler

By being a ParseNodeVisitor, the WHERE compiler visits the ParseNode for the WHERE clause and generates an **Expression**. Expression is an interface for expressing and evaluating expressions in SQL statements. Expressions naturally can be hierarchical. The Phoenix parser represents a WHERE clause with a ParseNode and the WHERE compiler translates it to an Expression. Expression has an accept() method to allow an ExpressionVisitor to traverse its expression tree. 

The main difference between an Expression and ParseNode is how the literal values are represented. In a ParseNode, they are expressed using their corresponding Java objects. For example, if the value of a literal is of type CHAR, it is expressed using the Java String class. However, in an Expression, the literal values are converted to the byte arrays, i.e., their on-disk representations. This allows Expressions to be evaluated over on-disk representations on both client and server side. 

## WHERE Optimizer

The main purpose of the WHERE optimizer is to identify the list of (primary) key ranges implied by the WHERE expression generated by the WHERE compiler. These key ranges are then used to determine the table regions to scan and generate a **SkipScanFilter** for each of these scans if applicable. 

The WHERE expression may include non-PK column (sub) expressions. After identifying the key ranges, the WHERE optimizer removes the nodes for PK columns from the expression tree if these nodes are fully used to determine the key ranges.

Since the values in the WHERE expression are expressed by byte arrays, the key ranges are also expressed using byte arrays. KeyRange represents a range for a row key or any sub part of a row key. A key range is composed of two pairs, one for each end of the range, lower and upper. The pair is formed from a byte array and a boolean value. The boolean value indicates if the end of the range specified by the byte array is inclusive or not. If the byte array is empty, it means that the corresponding end of the range is unbounded. 

We will use the notation for a key range that includes parentheses and brackets where parentheses are used to indicate exclusive ends of key ranges and brackets indicate inclusive ends. So, an integer key range of (5, 8\] means the range includes integer values 6, 7, and 8 but not 5\. 

Please note that this notation will be used to represent the key ranges for illustration purposes here and should not be confused with the usage of parentheses in the WHERE expression. For example, parentheses are used in WHERE expressions for Row Value Constructors (RVCs) such as (PK1,  PK2) \> (100, 25\) which mean the values for a primary key composed of two leading primary key columns PK1 and PK2 should be greater than the primary key value constructed from the column values 100 and 25 for columns PK1 and PK2.

A **KeySlot** represents a key part and the list of key ranges for this key part where a key part can be any sub part of a PK, including leading, trailing, or middle part of the key. The number of columns in a key part is called *span*. For the terminal nodes (i.e, constant values) in the expression tree, KeySlot objects are created with a single key range. When KeySlot objects are rolled up in the expression tree, they can have multiple ranges. For example, a KeySlot object representing an IN expression will have a separate range for each member of the IN expression. Similarly the KeySlot object for an OR expression can have multiple ranges similarly. Please note an IN operator can be replaced by an equivalent OR expression. 

When the WHERE optimizer visits the nodes of the expression tree, it generates a **KeySlots** object. KeySlots is essentially a list of KeySlot objects (please note the difference between KeySlots vs KeySlot). There are two types of KeySlots: **SingleKeySlot** and **MultiKeySlot**. SingleKeySlot represents a single key slot whereas MultiKeySlot is a list of key slots the results of AND expression on SingleKeySlot or MultiKeySlot objects. 

A **RowKeyValueConstructorExpression** node is constructed of **RowKeyColumnExpression** nodes in the expression tree. For each RowKeyColumnExpression node, a separate SingleKeySlot is created initially. When the SingleKeySlot objects are rolled up, a separate SingleKeySlot object is created for each maximum span of consecutive columns of a RowKeyValueConstructorExpression node. In other words, the SingleKeySlot objects RowKeyColumnExpression nodes within a span are merged and each span is represented by a single key range. For example, the expression node that includes RVC expressions for (PK1,PK2) \> (2, 5\) is represented by a SingleKeySlot object and the key slot in this object has one key key range. Please note the lower bound of this key range is the byte array representation of (2, 5\) and the upper bound is unbounded (i.e., the empty byte array). However, if the RVC expression includes more than one maximum span as in (PK1, PK2, PK4, PK5) \> (2, 5, 1, 8), then two key slots are generated, one for each maximum span of columns. If the RVC expression is the form of (PK1, PK2, ….) \= (V1, V2, ….), then it is translated into (PK1 \= V1 AND PK2 \= V2 AND …).

### AND Operation On Key Slots 

As mentioned before, the key slots are rolled into a MultiKeySlot object when processing an AND expression. The AND operation on two key slots starting their spans with the same PK columns is equivalent to taking intersection of their ranges. If the spans of these key slots are different, the current implementation clips the range of the key slot with the larger range and then does the intersection. The clipped range is then added to a list of trailing ranges and processed later. This is done by iterating over all unique combinations of key ranges in the list of trailing ranges and then intersecting them.

The KeySlots objects are processed in the order of their PK column position. If any of KeySlots objects in the list is the empty key slot, the result is the empty key slot.

### OR operation on Key Slots

The OR operation implementation is limited and rather simple compared to the AND operation. The OR operation attempts to coalesce key slots if all of the key slots have the same starting PK column. If not, it generates a null KeySlots.

### Extracting Expression Nodes

When an expression node is used fully in generating a key slot, this expression node is removed from the expression tree. This optimization is to eliminate the redundant HBase filters for the expression nodes that are fully covered by key slots.

# Issues with Current Implementation

Before we describe some issues with the current implementation, we need to understand why generating key ranges for arbitrary expressions is an intractable problem and needs to be treated very carefully. 

A row key for a given table can be composed of several PK columns. A row key is equivalent to a point in a multidimensional space where each PK column corresponds to a separate dimension in the space. A key slot is a subspace in this space. Without any restrictions imposed by predefined rules, intersection of key slots can lead to a large number of key slots, i.e., key ranges. For example, consider a row key composed of three integer columns, PK1, PK2, and PK3, and the expression (PK1,  PK2) \> (100, 25\) AND PK3 \= 5\. The space for the row key is a three dimensional space. Each of the expressions (PK1,  PK2) \> (100, 25\) and PK3 \= 5 represent a section (a subspace) in this space. The AND operation on these subspaces is equivalent to 

1. Overlapping these subspaces, and   
2. Finding their intersections. 

The result would be a very large number of key slots and each key slot represents a point in the three dimensional space, including (100, 26, 5), (100, 27, 5), …, (100, 2147483647, 5), (101, 1, 5), (101, 2, 5), … . Please note a point is a range where lower and upper bounds are the same bounded value. 

Let us consider a much simpler example where a row key is composed of two integer columns, PK1, and PK2, and the WHERE expression is (PK1,  PK2) \> (100, 25\) AND (PK2 \< 15). Even this seemingly very simple example can generate a very large number of key ranges. These are  \[(101, \-2147483648), (101, 14)\], \[(102, \-2147483648), (102, 14)\], …, \[(2147483647, \-2147483648), (2147483647, 14)\]. Please note inner parentheses express key values formed from a pair of column values and other brackets express key inclusive key ranges.

These simple examples with a relatively small number of PK columns and a simple data type, integer, is sufficient to show that finding key ranges for an arbitrary expression is an intractable problem. Attempting to optimize the queries by enumerating the key ranges can lead to excessive memory allocation and long computation times and the optimization can defeat its purpose. 

The current implementation attempts to enumerate all possible key ranges in general. Because of this, the WHERE optimizer has caused out of memory issues, and query timeouts due to high CPU usage. The very recent bug fixes attempts to catch these cases and prevent them. However, these fixes do not attempt to cover all cases and are formulated based on known cases.

In addition to inefficient resource utilization, there are known types of expressions, the current implementation still returns wrong results for them.  For example, please see [this open issue](https://gus.lightning.force.com/lightning/r/0D5EE00000vRXCF/view) where if degenerate queries are caused by some conditions on non-leading PK columns, then Phoenix cannot catch this and can return wrong results.

An example to show inconsistencies in the implementation is as follows. An RVC expression can be converted to an equivalent AND/OR expression. For example, (PK1, PK2) \> (A, B) is equivalent to (PK1 \> A) OR (PK1 \= A AND PK2 \> B). The implementation converts the first expression into a single key range and thus a scan with the start and stop rows keys without a filter. However, the implementation cannot do the same for the second expression and instead it generates a scan with a filter for the expression without generating a key range.

Due to tens of possibly conflicting bug fixes over the years and not having a document that clearly describes the design, the current implementation has become hard to understand and maintain. 

The classes and operations the WHERE optimizer uses are not clearly separated. There are several similar but still different and thus confusing operations defined for KeyRange. These are coalesce(), union() and concat().  KeySlot can have multiple ranges and MultiKeySlot by having multiple KeySlot objects can also have multiple ranges. It requires debugging and code walkthroughs to see how they are used.   
There are only two operations defined on KeySlots: AND or OR. The descriptions for these operations given in the previous section are at the high level. This is because explaining next level details is very difficult without describing the code verbatim. Not being able to abstract the details is due to several special cases in the code. This is one of the reasons that makes the code hard to understand and maintain.

# WHERE Optimizer Redesign

The WHERE optimizer redesign is formulated based on the following observations:

1. As described in the previous section, attempting to enumerate the PK ranges over arbitrary expression is an intractable problem due to key range explosion. Since identifying key ranges is just for the optimization but not for the correctness of queries, the cost of optimization should justify the gain from the optimization.  
2. The optimization gain comes from first skipping table regions and then skipping rows within table regions. In practice, the most gain comes from the most significant leading PK columns. The optimization is not useful if the first leading PK column is not included in a WHERE expression. The value of the optimization decreases with the subsequent PK columns. 

The objectives of the redesign are as follows:

1. The space and time complexity of the WHERE optimizer should not be more than O(N2).  
2. The redesign should be provably correct. This requires constructing a mathematical system with well defined elements and operations.   
3. The redesign should generate the same result for the expressions that are logically equivalent.   
4. The redesign should lead to significantly simpler implementation. This can be achieved using well defined and clearly separated operations and concepts.  
5. The scope of the redesign will be limited to the WHERE optimizer and so the changes will mostly be limited to where optimizer and Expression classes. For example, this redesign does not attempt to change the skip scan filter design or the WHERE compiler. 

## Mathematical System

We first translate an arbitrary WHERE expression into a WHERE expression where RVC, IN, BETWEEN and so on expression nodes are replaced by their equivalent AND/OR expressions. This is done for two purposes. One is to build a mathematical model from simpler constructs and the other to make sure that logically equivalent expressions give the same result.

Based on the problem domain analysis, we will not represent expressions using the concepts of key range, key slot, key part and key slots but simply using the concept of key space. A key space is specified by an array (i.e., ordered set of) of ranges, one range for each dimension.The entire key space, i.e., the key space universe, of a table with N PK columns is an N-dimensional space where dimensions correspond to PK columns. The ranges for the dimensions of are defined by the data types of the corresponding PK columns. For example, if the PK column is of type INTEGER, the range for the corresponding dimension is the range for integers, i.e., \[-2147483648, 2147483647\].

A range can be considered as a set of distinct values in the range. A row key can be considered as a tuple of values of its PK columns. A tuple, thus, a row key can also be viewed as an ordered set. The set of all row keys defined by a key space is generated by taking the cartesian product of the ranges (or the sets of distinct values) of the dimensions. By definition, a cartesian product of the sets are the all possible ordered combinations consisting of one member from each of those sets.  

Although both a key space and a key range represent a collection of keys, they are different. A key space can map to a set of key ranges, and similarly a key range can map to a set of key spaces. The difference comes from the fact that the set of keys in a key range covers all the keys between the minimum and maximum key of the set (by the definition of a key range). However, a key space may not cover all the keys. Consider a two dimensional key universe where the range for a dimension is \[0, 8\]. The following diagram illustrates the case where a key range \[(2,4), (5,8)\] shown by the blue area maps to two key spaces (green rectangles).

 

Each expression node will be represented as a collection (a list or set) of N-dimensional key spaces. Some expression nodes can be represented by a single key space but not all of them. That is why we need to represent them by a list of key spaces in general.

For example, a table with three PK columns (PK1, PK2, PK3) has a 3-dimensional key space. Every expression node will be a list of 3-dimensional key spaces. For example, the expression PK2 \>= 3 is a key space where the ranges for PK1 and PK3 columns include all values for their data type (which will be represented by  (\*, \*)), and the range for PK2 is \[3, \*). This means the key space for this expression is the array \[(\*,\*), \[3,\*), (\*,\*)\], more accurately the expression is represented by a singleton list with that array.

To visualize a three dimensional key space as a geometric shape, consider them as boxes where each side of the box is defined by the ranges (intervals) of two dimensions. We allow ranges to include a single value. If the ranges for all dimensions are single valued (for example as in the expression PK1 \= 2 AND PK2 \= 5 AND PK3 \= 8), then this key space corresponds to a point (a special form of a box). Each side of the box can be a point, a line or a rectangle.

Now, we can define AND or OR operations on a pair of key spaces.

The AND operation on a pair of key spaces is a key space that is obtained by intersecting key spaces. This intersection could be the empty key space. The intersection of two key spaces is equivalent to the intersection of the ranges of the dimensions independently.

Consider the following example: \[(\*,\*), \[3,\*), (\*,\*)\] AND \[\[2,\*), (\*,5), (4,7)\]. This will give \[\[2,\*), \[3,5),(4,7)\]. However, \[(7,\*), \[3,\*), (\*,5)\] AND \[(\*,7), (\*,1), (4,7)\] will result in the empty space.

The OR operation on a pair of key spaces obtained by taking union of the key spaces. The result of the union operation cannot always be represented by a single contiguous key space. Thus, the result of the OR operation is a list of key spaces in general. In other words, the union of two key spaces is either the original list of key spaces (in this case, the OR operation becomes a no-op) or a single key space. To see this consider taking the OR (union) of two row keys of a table. If the row keys are consecutive, then the result will be a row key range that includes these two row keys. However, if the row keys are not consecutive or the same, the OR operation will be a no-op, that is, the result will be the list including these row keys. 

The OR of two key spaces with N dimensions can result in a single key space, that is, the key spaces are merged into one, only if one of the following conditions is satisfied.

1. One key space is completely contained within another key space. In this case, the result of the OR operation is the larger key space.  
2. The key spaces have the same range for at least N \- 1 dimensions and the ranges for the remaining dimension cannot be disjoint. In this case, the range of a dimension of the resulting key space is the union of the corresponding ranges of the two input key spaces for this dimension.

To see the need for the second condition visually, consider two rectangles (key spaces) in a two dimensional space. These rectangles can form another rectangle if the ranges for at least one dimension have to be the same and the ranges for the other dimension have to be non disjoint.  In the following diagram, blue rectangles cannot form another rectangle but the green rectangles can do.

Similarly, in the following diagram, blue boxes (key spaces) in a three dimensional space cannot form another box but green boxes do.

Consider the following example: \[\[1,1\], \[3,7), (\*,\*)\] OR \[\[1,1\], (6,9), (\*,\*)\]. This will give \[\[1,1\], \[3,9), (\*,\*)\]. However, \[(7,\*), (\*,8), (4,7)\] OR \[(\*,7), (\*,8), (4,7)\] will result in the list (\[(7,\*), \[(\*,8), (4,7)\], \[(\*,7), (\*,8), (4,7)\]) because the union of two ranges for the first dimension results in two ranges (\*, 7\) and (7, \*) because they are disjoint.

This counter intuitive representation of seemingly a point like expression PK2 \= 5 by the 3-dimensional key space  \[(\*,\*), \[5,5\], (\*,\*)\], more accurately a singleton list with that array, is the key point behind the mathematical model here. The reason for this representation is that PK2 \= 5 by itself is not sufficient to express a useful row key range and it needs to be combined with other expressions to form a row key prefix or full row key. The logic of combining expressions using AND (intersection) or OR (union) operations requires expressions to be treated as 3-dimensional key spaces in this example. For example, PK1 \= 2 AND PK2 \= 5 will yield to a row key prefix 25 and this can be obtained easily by intersecting \[\[2,2\], (\*, \*), (\*,\*)\] and \[(\*,\*), \[5,5\], (\*,\*)\] with a rather simple intersection algorithm as defined above. Probably a more convincing example would be PK1 \= 2 AND PK2 \= 5 AND PK3 \> 8\. The corresponding key spaces to be intersected will be \[\[2,2\], (\*, \*), (\*,\*)\],  \[(\*,\*), \[5,5\], (\*,\*)\] and \[(\*,\*), \[\*,\*\], (8,\*)\]. In this case, the result will be \[\[2,2\], \[5,5\], (8,\*)\].

The mathematical system we defined so far is not closed under AND/OR operations because we defined them as binary operations on key spaces and the result of these operations can be a list of key spaces not just a single key space due to the OR operation. This requires us to extend these operations to lists of key spaces. Please note that the mathematical model can be considered as an abstract algebra model where binary operators are defined on a set of elements. The elements will be lists of key spaces rather than the key spaces. This distinction is important for the implementation but  does not really matter for the structure of the abstract algebra model. The model does not care if the elements are lists, sets, matrices, shapes, numbers, etc. It only cares if the operations are well defined on them and the system is closed under these operations.

It is straightforward to extend the AND operation on a pair of key spaces to N key spaces by doing a rolling AND operation (i.e., take the AND of the first two key spaces which result in a single key space and take the AND of this result and the next key space, and so on). The result of this rolling AND operation will be a single key space too.

As explained previously, the OR operation on a pair of key spaces is either a no-op or merging them into one key space, that is, this operation can yield one or two key spaces.  Similarly, the OR operation on N key spaces can yield n key spaces where n \= 1, 2, …, N.  

The OR operation on N key spaces is done by first taking the pairwise OR of the key spaces. If any of these OR operations results in a merge, that is, if the union of two key spaces can be represented by one, the merged key spaces are replaced by their merges. The OR operation is then applied to the new set of key spaces until no more merges. Please note if a merge case never happens then the OR operation over N key spaces is a no-op.

Now, we need to define AND and OR operations on a pair of lists of key spaces. 

We know that the AND operation on a list of key spaces results in one key space (including the null key space). During the roll up of the AND or OR operations on the expression tree, if we see a list of key spaces, we know that that is because of the OR operation. This means that when we take the AND of two lists of key spaces, we are doing AND over OR operations.  As in the case of (A OR B) AND (C OR D) \= (A AND C) OR (A AND D) OR (B AND C) OR (B AND D), we need to distribute AND over OR which means we will take the AND of every pair of key spaces one key space from each list and then take the OR of the results of AND operations.

For a concrete example for this, consider the expression (PK1 \= 5 OR PK1 \= 10\) AND (PK2 \= 1 OR PK2 \= 4\) for a table with two PK columns. When we roll up the expressions in the expression tree for this example, we will take the AND of two lists at the root of the tree: (\[\[5,5\], (\*,\*)\],  \[\[10,10\], (\*,\*)\]) and (\[(\*,\*)\], \[1,1\]\], \[(\*,\*), (4,4)\]). The result will be (\[\[5,5\], \[1,1\]\], \[\[5,5\], \[4,4\]\], \[\[10,10\], \[1,1\]\], \[\[10,10\], \[4,4\]\]) as expected when we distribute AND over OR.

The OR of two lists of key spaces is equivalent to the OR of the combined list of key spaces as in the case of (A OR B) OR (C OR D) \= (A OR B OR C OR D).

### Converting Key Spaces to Key Ranges

The set of key ranges for a given key space is determined using the ranges of leading dimensions of this key space. We call a dimension an everything dimension if the range for this dimension is everything, i.e., (\*,\*).

The trailing dimensions starting with the first leading everything dimension are not considered for generating key ranges. That is , the set of key ranges for a given key space is determined using the leading non-everything dimensions. If the first dimension of a key space has the everything range, the set of key ranges for this key space is everything, i.e., includes all row keys. 

Let *d1*, *d2*, … *dm*  be the sequence of the non-everything leading dimensions (i.e., PK columns) of a key space. The number of key ranges of this key space is determined by all dimensions except the last dimension in this sequence, i.e., *dm*. Let *n1*, *n2*, … *nm-1* be the number of distinct values in the ranges for dimensions respectively. The number of key ranges will be *P* \= *n1* \*  *n2* \* … \* *nm-1*. The first *m \- 1* dimensions will yield *P* key prefixes. These key prefixes are generated by taking the cartesian product of the ranges of the first *m \- 1* dimensions. Then we concatenate these key prefixes with the key range of the last dimension (*dm*) to get *P* key ranges. Please note if there is only one non-everything dimension then this key range for this dimension is the key range for the key space.

Let *p* a key prefix (for the first *m \- 1* dimensions, i.e., PK columns) and *r* be the range (for *dm*). If the lower bound for *r* is unbounded then the key range will be (\*, *p.u*\], and if the upper bound for *r* is \* then the key range will be \[*p.l*,\*), otherwise the key range will be \[*p.l*, *p.u*\] where *l* and *u* are inclusive lower and upper (unbounded) values for *r* and the “.” operation is the Phoenix row key composition operation to generate the row key from column values.

## Design Details

The redesign of the WHERE optimizer is centered around the concept of key space that allows the WHERE optimizer time and space complexity to be bounded by O(N2) rather than intractable as the case with the current implementation. 

To see this, we can use the previous example where a row key is composed of three integer columns, PK1, PK2, and PK3, and the WHERE expression is (PK1,  PK2) \> (100, 25\) AND PK3 \= 5 (in section Issues with Current Implementation). The expression generates a very large number of key ranges including (100, 26, 5), (100, 27, 5), …, (100, 2147483647, 5), (101, 1, 5), (101, 2, 5), … . The exact number is (2147483647-99)\*(2147483647). Since the current implementation generates these key ranges while traversing the expression tree, it leads to excessive memory and CPU usage. 

This WHERE optimizer can decide at what level of granularity (more accurately at what level of dimensionality) the PK ranges should be expressed (for scans and skip scan filters) during the list of key space computation for expression trees. Before converting key spaces to key ranges, we can see that converting this key space into key ranges would result in key range explosion and thus, we need to use lower dimensional key spaces by simply dropping one or more trailing dimensions. For the above example, instead of using the three dimensional key space, we use its two dimensional counterpart. This is will result in just one key range, \[(100, 26), (\*,\*)\] (note here (100,26) is the prefix of the row key where PK1 \= 100 and PK2 \= 25\.  As we observed before, the most optimization gain comes from the leading PK column, and thus we clip the trailing PK columns to prevent key range explosion.

In the previous section, we show that a key range can map to a set of key spaces. This implies that after converting key spaces for the entire WHERE expression to the key ranges, some key ranges can still merge. Thus, we sort the key ranges and merge the adjacent or overlapping key ranges. Please note that key ranges will be on row key prefixes or full row keys and thus merge operation will be rather straightforward.

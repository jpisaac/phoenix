## 1. Introduction

In Salesforce 1P, HBase supports disaster recovery (DR) by putting two clusters in master-master mode. Data is replicated from one cluster to the other in an [asynchronous](https://docs.google.com/presentation/d/12yHoOje5vMQudibJLXEoEeuEezCFxoPpJn_7QUXLMfg) way. HBase is a [shared](https://docs.google.com/presentation/d/1Oc1VLojHi1vWB5Op1SUAWCSwo8H2DVsnwlAVIdngeR8/edit) service at SuperPod/Kingdom level across multiple Salesforce Pods. When one Pod in 1P is not healthy, we failover all its traffic to another Pod. The failover is done at Salesforce Pod level in CoreApp by switching to the other set of CoreApp servers in another data center (DC) that talk to their corresponding HBase cluster. HBase clients will never failover from on cluster to the other - they always connect to the HBase cluster which is in the same DC. In Falcon, the CoreApp deployment will not support DR essentially. CoreApp, as the largest HBase application, sets its cloud native strategy 3AZ and will not include out of region DR. The arguments we do not have default DR in Falcon is mainly about reduced cost to serve.

However, we HBase team still believe supporting HBase DR failover would be affordable and helpful in Falcon, including but not limited to following advantages:

* *Improved HBase availability.* HBase service is running as a stack of big data services including multiple distributed components: ZooKeeper, NameNode, DataNode, JournalNode, HMaster, RegionServer, ResourceManager, NodeManager etc. Any layer of unavailability may degrade HBase service overall availability. Having a pair of HBase clusters working in active-standby mode, CoreApp can failover to the standby HBase cluster when the current active one is deemed unhealthy. From the HBase replication’s point of view, the replication is still in master-master mode.
* *Reduced operational failure blast radius.* By running a pair of clusters HBase service is able to better tolerate operational issues. For example, planned events like disruptive major version upgrade on one cluster will not cause any service down time. Unplanned events like cluster misconfiguration, corner case bugs in code, Kubernetes infrastructure failure can also be mitigated in presence of failover feature.
* *Off-loaded analytics.* It’s possible in future that analytics could read directly from standby cluster instead of the active one. The gain is significantly reduced load on the active HBase cluster, which could serve online requests with better latency and throughput. The restriction here is that, reads from standby cluster will have to trade off strong consistency if the replication is still asynchronous. This is not a big concern for most (possibly 99.9%!) analytic jobs.

This major concern about CTS is discussed more in [Section 6](https://salesforce.quip.com/DWXzAwWla7bV#DXaACA3RI1y). One important design principal of HBase DR in Falcon is that, all clients (CoreApp) in a Falcon a [functional domain](https://docs.google.com/document/d/17Nl1mPfkRNL7IYaShk8sJlhme1NgzPLgK8p80fXr7TY) (FD) will be partitioned into groups, and each group will have its own definition of “active” and “standby” for the shared two HBase clusters. This is natively supported in Falcon architecture via the concept of Cells. Basically every CoreApp Cell will be in a failover group, where one of the two HBase clusters is considered “active”. This way, we have much of the flexibility to direct HBase traffics to the two HBase clusters at the same time. Overall the total number of HBase servers are not necessarily doubled. Another concern of HBase DR clusters is about operational cost - after all we have doubled the number of HBase clusters. Hopefully operational cost is increased but not significantly, thanks to the full deployment automation (provision, rolling update, and scaling) in Falcon.

To enable DR in Falcon, we first need to provision two HBase clusters when deploying HBase service in a FD. This includes an infrastructure as code (IaC) pipeline and a Kubernetes deployment pipeline for each of the two HBase clusters. The two HBase clusters will then be paired as peers to each other and be enabled replication accordingly. For all clients in a failover group, one HBase cluster is in *active* role and the other *standby* role. At any time, a CoreApp server (called “client” in this doc) only talks to the active HBase cluster. A cluster role transition can be triggered by human operator or an external system indicating active and standby clusters switch roles. For starters, the transition action will be taken manually. In future this functionality can be hooked up with the health of HBase clusters. Since replication at HBase level is asynchronous, there is no built-in strong consistency guarantee after failover. In this design, consistency is supported with best effort. We will discuss techniques to improve the consistency guarantee and availability.

### **1.1 Roadmap**

There are different levels of support for failing over feature to improve HBase service availability. On our roadmap, we will move gradually from the following list.

1. ***Manual failover*** is supported now by overriding the `hbase.xml` configuration file and restart all CoreApp servers.
2. ***Push-button failover*** is triggered by human operator and once a trigger is detected, CoreApp will fail over automatically without restart. This is the scope of this design doc. Human has to monitor and push a button to trigger a failover. Specially, cluster role can change again when we trigger failover back to a cluster. Anytime a cluster role transition happens, the current active HBase clusters is not active any more. There will be logic to close all Phoenix connections and blocks incoming requests to this HBase cluster. Common use cases are supported as following:
    1. *Use cases favoring availability*: the push-button failover can simply switch the two clusters’ role. All clients upon detecting the role transition will immediately failover to the other cluster.
    2. *Use cases favoring best-effort consistency:* operator can first put both clusters into “standby” role and wait for the replication to target cluster is done. Operator will then put the target cluster “active” after which clients will talk to the newly active cluster. During the interval when both clusters are “standby”, the HBase service is considered “unavailable”. This interval is controlled by operator, called 2-steps failover triggering.
    3. Use cases *disabling DR:* clients will need not configuration change and this DR feature is simply disabled by default. Alternatively, the table replication can be disabled if no failover ever is required.
3. ***Automatic failover*** will not require human proactive operation (can still need a manual approval) or CoreApp server restarts. It will integrate with cluster health check to automatically trigger the failover. This design doc does not address this problem, and we will have V2 design doc to integrate with automatic failover. The major difference between “push-button” and “automatic” failover is that, in this automatic failover, it is an external system not human operator that collects all health/replication context and triggers failover.

### **1.2 MVP Requirements**

To provide a minimum viable product (MVP), we target the **2.** ***push-button failover* **with best-effort consistency guarantee. The project planning and status can be tracked by [this GUS report](https://gus.lightning.force.com/lightning/r/Report/00OB0000003AASJMA4/view). Specifically,

1. Ability to switch underlying HBase cluster used by CoreApp in a Cell based on a manual event.
2. CoreApp will detect the cluster role transition and failover to the target HBase cluster without restarting. The latency of detection and failover should be small (SLA is TBD).
3. Phoenix connections in CoreApp will be informed a failover is happening and/or just happened. Otherwise, clients may effectively lose read-your-writes consistency and application level data inconsistencies can easily result.
4. There will be Argus metrics and Splunk logs to reason about clients’ status of failing over.
5. Avoid re-architecture or heavy diverge with solutions to [related works](https://salesforce.quip.com/DWXzAwWla7bV#DXaACAE41Tq) on both 1P and Falcon.

## 2. Problems

There are several tasks we need to address for HBase DR in Falcon for CoreApp. Some of them are counterpart work of 1P, for e.g. cluster deployment and peering. The provisioning part in Falcon has been taken care of by our Spinnaker pipeline which [creates a pair of EKS clusters](https://spinnaker.sfcd.gcp.sfdcsb.net:9000/#/applications/bdstoragehbase/executions?pipeline=driver-eks-iac-v2) and deploys HBase manifests on top of them. See [this](https://spinnaker.sfcd.gcp.sfdcsb.net:9000/#/applications/bdstoragehbase/executions/configure/1065f35f-af10-43af-ada9-43743fdd6e7d) as an example. The HBase replications between the two HBase clusters works in the standard bi-directional way once they are peered and table (more accurately, column family) replication is enabled. The other problems mainly come from the major difference between how CoreApp connects to HBase in 1P and public cloud.

### 2.1 Assumptions

* ***_Falcon_ vs. 1P.* **In 1P, the async replication between two HBase clusters are between two data centers via Internet (50ms -ish). In Falcon, the replication is within the same functional domain, essentially the same VPC in the same region (3ms -ish). This means the replication lag between two Phoenix/HBase clusters in Falcon should be significantly smaller than in 1P. Both CoreApp and Phoenix/HBase clusters are across 3AZ in a FD, so client and server traffic may be inter-AZ. This doc assumes the overall design and implementation is based on Falcon architecture. Solutions here *may* not work *directly* in 1P for the same HBase DR problem in CoreApp. The goal here is to make the interface to client generic while implementation can be different between 1P and Falcon, assuming it’s easily pluggable. Even in Falcon, the implementation details can also be substrate specific. We will try to avoid re-architecture or heavy diverge with solutions to [related works](https://salesforce.quip.com/DWXzAwWla7bV#DXaACAE41Tq) on both 1P and Falcon. 
* ***Security***. For Kerberos authentication and over-the-wire encryption, an HBase client uses the same KeyTab to talk to both HBase clusters. With Kerberos as a service (KaaS), all the HBase clusters in a single FD [belong to the same realm](https://salesforce.quip.com/TdtmAZbXTFV6).
* ***SAM.*** Would problems be simpler if HBase service and CoreApp are deployed in the same Kubernetes cluster? Definitely. For example, the source-of-truth will be local to an Kubernetes cluster and detection can be watching events delivered by API server. In Falcon, CoreApp is deployed via [Salesforce Application Model](https://confluence.internal.salesforce.com/display/SAM/Salesforce+Application+Model+%28SAM%29+Home) (SAM) environment, that means we need to deploy HBase in SAM as well. Before HBase is fully onboarded onto Falcon Kubernetes Platform (FKP), we assume CoreApp and HBase are running in different Kubernetes clusters in Falcon, while the HBase clusters for DR are also running in different Kubernetes clusters to reduce radius blast of infrastructure failure.
* ***_Async_ vs. sync replication.*** We use asynchronous replication for this design, so any new design favoring synchronous replication will be discussed in a separate doc. The reasons are three-fold: *1)* the synchronous replication is not available in HBase 1.x and backporting this feature from 2.x needs major development effort which we can not commit now; *2)* existing synchronous design in community reduces overall availability since it depends on availability of two HBase clusters - remember increased availability is our first goal here to have DR feature; *3)* this feature is not well tested or performant because of extra I/O time for write.
* ***PQS*.** The problems and design in this doc are based on currently how CoreApp uses HBase via fat Phoenix client. In the long term, we should move to a PQS based architecture, where HBase use cases in CoreApp talk only to PQS as their point of interaction. This enables us to do failover management completely at our layer and in a client agnostic way. Before that, we need to address the HBase connections coordination between clusters at CoreApp servers side.
* **Server vs. client coordination.** The reality so far is that two HBase clusters do not know their roles so they do not fence client requests if they are in “standby” role. The two clusters are enabled with master-master replication, and any client requests will be accepted. There is no fencing mechanism implemented or required in HBase according to its cluster role. Clients, will need to be coordinated regarding the “active” cluster to use. Let’s revisit this in section 3.4.

### 2.2 Problems

1. **How clients detect cluster role transition?
    **A client can not make this decision by itself based on its connection status because a client has not enough context to infer this information independently. Failing to connect to active cluster does not imply this client should fail over to the other cluster blindly. The source-of-truth as we mentioned above, will be manually maintained by current design. Future work will make active-standby transition automatic depending on HBase cluster health and optional human approval. Given that, how clients detect cluster role transition largely depends on the metadata store we choose. The most straightforward one is periodic polling at client side (*active approach*). The poll should be lightweight so that the overhead (latency and resource usage) and the interval can be both small enough (in seconds instead of minutes). Alternatively, the failover detection can be event-driven (*passive approach*). For example, clients get notified (for e.g. via [ZK watcher](https://zookeeper.apache.org/doc/r3.4.13/api/org/apache/zookeeper/Watcher.html)) when the active-standby transition happens. Clients do not communicate with each other and this transition detection is implemented separately in every client aka CoreApp JVM.
2. **How to make client stop current connection and start using the new cluster?
    **To failover, all current Phoenix connections in a CoreApp will be closed. This can be done by a monitor thread which detects cluster role transition and closes all open Phoenix connections. CoreApp client will get an exception when it tries to use a closed Phoenix connection. When retrying its business logic, the client will get a new Phoenix connection to the newly active HBase cluster, meaning failover has happened and informed to the client. This part is not transparent to client so that client can handle potential inconsistency specially if necessary. Most use cases are pretty immune from these unexpected inconsistency issues. They use immutable tables and do not expect consistency across rows or tables. So for them, they can simply get a new Phoenix connection in case of this failover exception. Meanwhile, all incoming request to standby cluster should be blocked.
3. **How to support consistency during failover?
    **In case of failover happens, a client may not be able to read its own writes and writes of one client may not become visible to any other clients. Work can be done to minimize the window in which this is the case but cannot close it completely. Andrew [suggests](https://salesforce.quip.com/EcRLAFdXqnY0#GUbACA8qFxA) it would be better to fail all work in progress at the switch point and allow recovery mechanisms to do the right thing. Trying to hide the switch over is believed to hide too much about how the underlying assumptions of consistency have been suddenly invalidated by the switchover. The main problem comes from the asynchronous replication. Human operator will decide when to put a cluster “active”. She can simply switch the two clusters’ role so that clients will immediately failover to the other cluster. Or she can first put both clusters into “standby” role, wait for the replication to be done, and last set the target cluster “active”. During the interval when both clusters are “standby”, the HBase service is “unavailable”. As to how human operator makes this decision wisely, there are practical problems to implement. For MVP we will provide such flexibility of failover trigger that best-effort consistency is supported during failover.

## 3. Design and Implementation

As we mentioned in [Roadmap](https://salesforce.quip.com/DWXzAwWla7bV#DXaACAlxqJN) section, the simplest way to failover to a new HBase cluster in CoreApp, is to restart CoreApp. When restarts, new and fresh active HBase context will be set up and all connections are created on latest active HBase cluster. This is the *simplest* approach to failing over all clients from HBase service’s point of view. It seems not very blessed by folks out of HBase team because restarting all CoreApp servers connecting to one HBase cluster is a very resource- and time-consuming process. This design supports existing clients without restarting.

This doc is a to propose a new HA policy in the Phoenix HA framework, which will enable client connections to switch between to two HBase clusters for higher availability in an coordinated way. For more information about high level architecture, please see [Phoenix Client High Availability Framework](https://salesforce.quip.com/6THcAlQ8aDBc).
As Figure 1 shows, every CoreApp server will have multiple HA groups, each of which has an active HBase cluster and a standby HBase cluster. All clients in that HA group will talk to the same active HBase cluster. Failover the HBase clusters for an HA group will only change the HBase cluster role for the HA group, without affecting other groups. After failover, all clients in the HA group will connect to the other HBase cluster namely the newly active HBase cluster. More details can be found in the design doc [Phoenix Client High Availability Framework](https://salesforce.quip.com/6THcAlQ8aDBc). Specially, this doc covers some important design considerations, mostly from applications’ point of view.

### 3.1 Close current connections

***3.1.1 How client works with HBase/Phoenix connections now?***

First, the way to get a `PhoenixConnection` object is very standard in Java data base connection (JDBC) world:

```
Class.forName("org.apache.phoenix.jdbc.PhoenixDriver");
Connection con = DriverManager.getConnection("jdbc:phoenix:zk1,zk2,zk3:2181:/hbase");
// using con...
con.close();
```

As we can imagine, the real logic which creates a `PhoenixConnection` object talking to an HBase cluster is happening in the singleton `PhoenixDriver` class. This class, implementing the `java.sql.Driver` interface, creates a new `PhoenixConnection` in the `connect(String url, Properties info)` method which get called by `DriverManager` above.  `PhoenixDriver` does not create a new HBase connection for each new Phoenix connection in its `connect()` method implementation. The reason is that, [HBase connection creation is a heavy-weight operation](https://hbase.apache.org/apidocs/org/apache/hadoop/hbase/client/Connection.html). The connection object contains logic to find the master, locate regions out on the cluster, keeps a cache of locations and then knows how to re-calibrate after they move. So HBase connections are shared by multiple Phoenix connections against the same HBase cluster and properties. Since those Phoenix connections usually are across multiple threads, a question is: *do they have race conditions?* Apparently, HBase connection implementations are thread-safe, so that the client application (e.g. CoreApp) can create a connection, cache it and share it with different threads. [`Table`](https://hbase.apache.org/1.2/apidocs/org/apache/hadoop/hbase/client/Table.html) and [`Admin`](https://hbase.apache.org/1.2/apidocs/org/apache/hadoop/hbase/client/Admin.html) instances in HBase, obtained against an HBase connection object, on the other hand, are light-weight and are not thread-safe. That being said, Phoenix connection object is designed to be a thin object that is inexpensive to create due to the underlying cached and/or shared HBase connection. Phoenix Connections should not be shared across threads. There is no connection pool in Phoenix driver, unlike most of other kinds of JDBC connections, for bookkeeping Phoenix connection objects. As a result, closing a Phoenix connection will usually not cause its underlying HBase connection closed.

How `PhoenixDriver` multiplexes one HBase connection for multiple Phoenix connections? There is an intermediate layer, an interface named `ConnectionQueryServices`. This connection query service (CQS), when initializing, will create an HBase connection. Specially, this HBase connection is not shared with other CQSs. When being used, a CQS  creates `Table` and `Admin` for each individual `PhoenixConnection` operations. There is a cache in `PhoenixDriver` for all open query services. All Phoenix connections sharing the same cluster connection information (including ZK quorum, port, user, principal, and KeyTab), will get the same `ConnectionQueryServices` object from the cache. If there is not such object, a new one will be created and added to the cache. If all Phoenix connections using this query service are closed by clients, this query service may still not get closed immediately, hoping it may be useful again. The cached query service will expire after a long interval (default to 1 day) since it is lastly accessed.

***3.1.2 How to close all opened Phoenix connections?***

The proposal here is to implement a `FAILOVER` HA policy, which will bookkeep all CQS instances and their Phoenix connections for failover groups. This HA policy is on the path where all CoreApp clients obtain phoenix connections by default in Falcon. The `FAILOVER` policy will be plugged into the Phoenix HA framework so it can be used to close all existing open phoenix connections and CQS upon failover events. This way, we can force all clients to use the new ACTIVE HBase cluster. Assumption here is that the client that is using a phoenix connection closed by the failover mechanism will retry their operation resulting in a new Phoenix connection. To better guide client doing this instead of giving up retries on unexpected connection closed exception, we can add new state and assisting methods in Phoenix connection. Such connection bookkeeping logic can be something that we do “in” Phoenix itself rather than CoreApp. In CoreApp, a client can always get a vanilla `PhoenixConnection` skipping our connection factory. However, if the logic is in Phoenix driver, it is almost impossible for client to use it unexpectedly. Another benefit of being in Phoenix itself is that, this failover feature can be more easily borrowed to non-Core use cases like marketing cloud. One idea is to set the `closeReason` for a `PhoenixConnection` object. The reason can be used to guide client to retry in case of failover.

Alternatively, one may think of manipulating PhoenixDriver’s internal HBase connections, so client may failover using the same Phoenix connection. First, much of Phoenix has multi table dependencies - schema, sequences, indexes. HBase level mechanisms cannot know about these because HBase tables never depend on the state of others (exception: meta). Without properly handling such dependencies we get into all kinds of troubles with index consistency etc. Moreover, ideas like [HBase.MCC](https://github.com/tmalaska/HBase.MCC) does not work well either, which explores managing multiple HBase clusters at the HBase connection level itself. It manages reading/writing to multiple clusters internally by switching between the clusters if a response is not received within a configured limit. It supports only some operations and is not actively maintained since 2015. 

### 3.2 Consistency during Failover

To support consistency during failover, we need to monitor when replication is completed in the target cluster, or a timeout (say, 15 mins). This requires all writes are stopped on the source cluster and replication progress is observable. This can be supported by making both HBase clusters be in `STANDBY` mode. Remember in case of a cluster role transition (from `ACTIVE` to `STANDBY`), no new Phoenix connections can be created to a `STANDBY` cluster while all Phoenix connections will get closed. During the short time where writes are disabled, clients may get failover exception instead of closed connection exception because the service is believed temporarily unavailable. Meanwhile, we need to provide some dashboard of metrics to track the overall progress. When the replication is done, there can be another cluster role transition, by human operator or programatic trigger, to make the target cluster `ACTIVE`. This interval is not very long if both clusters are healthy and replication is smooth. We can assume the replication between HBase clusters in a FD in Falcon environment is much faster than replication between two DCs in 1P.

How can we know the replication is completed after disabling all writes in the source cluster? Ideally, HBase supports accurate replication status between the two HBase clusters from which operator can make decisions for a failover group. There are ideas to use replication marker to track the progress, and if that can be exposed to us at table level, those decisions when to failover eventually will be more informedly made by either human operator, or automatic trigger system. As Andrew suggested, if we were to use a sentinel like approach we have to make sure the updates are sufficiently linearized. Today we dispatch replication work to the remote cluster with region granularity, which is too fine grain. Probably the minimum useful granularity will be the table. To linearize updates by table we would need to modify replication to always send the data for a given table to a specific remote peer. The remote peer will then have a serialized view over the change stream for every given table, and can update watermarks for each table with confidence. Meanwhile, if [only base table is replicated](https://docs.google.com/document/d/1wHwpBnLYrTeHfG-GCt-EOfB2uAyCgsRhu5DXeV4NXI4/) and Phoenix atomically updates all the index tables, we will have less data to replicate, but we then need more context at the target cluster side regarding indexing status.

If the replication is not completed within a threshold like 1 hour, we need some timeout to force the failover anyway. In case of this fallback, any clients failing over to the other cluster may still suffer from inconsistency issues. This means in this situation we trade the strong consistency in favor of reasonable availability. This however is a rare case where the source cluster is totally broken or network is unreachable between the two clusters for a long time. The logic of cluster role detection and Phoenix connection closing logic will still be the same for this case. The main work for timeout can live out of CoreApp and Phoenix client, but in the control plan using BlackTab/Spinnaker.

## 4. Beyond CoreApp in Falcon

There are use cases like Gridforce/Pig/Spark that use Phoenix/HBase service but the client runs out of CoreApp. For example, in Gridforce jobs, the Phoenix/HBase client will be in the MapReduce jobs. The simple and recommended way of employing two HBase clusters for DR is at Job level. Before launching a new Job, the launcher first discovers the currently ACTIVE HBase cluster for their use case. The Job configuration will only have one HBase cluster’s endpoint, as of today in 1P and Falcon. All tasks in that Job will use that HBase cluster in the lifecycle of the Job. In case of failover or Job failure due to HBase being unavailable, the launcher simply will launch a new Job which uses the newly ACTIVE HBase cluster as target.

Alternatively, those use cases can deal with failover at connection level without cancelling the whole Job.  This is possible because Phoenix/HBase DR feature is implemented in the Phoenix client module instead of in CoreApp. They need to make changes in the application with following steps:

1. To get a connection, the JDBC URI should contain both HBase clusters’ endpoint, namely, the ZK ensemble. The JDBC properties should contain the high availability (HA) group name, which will be static during a Job’s life cycle.
2. In case of `FailoverSQLException` implement a retry logic as CoreApp use cases usually do, which closes failing connections, cleans up local context and opens new connections. Many these use cases should already have the capability of auto-retry at Task or Job level enabled by the runtime framework.

Those Jobs are usually composed of short-lived and massive containers at runtime. Each container will set up ZooKeeper connections to both clusters in order to handle infrequent failover events. As a matter of service protection, this approach is not recommended by HBase team.

While today we support Phoenix/HBase failover in 1P in the case of a Site Switch for the Core App, we do not yet support Phoenix/HBase failover *independent of* the Core App,  as described for Falcon. However, there is no obvious reason why we can not deliver it.

There are two related problems to address. The motivation to discuss them here is to consolidate the design and implementation efforts for this DR work with those problems solving. Again, this is the first time in CoreApp, the client is aware of multiple HBase clusters, comparing currently in 1P all clients in the same CoreApp deployment connects the single shared HBase cluster regardless of its health status.

## 6. Discussions

There are open questions we need to address and here is the discussions on them. Anything listed here are considered non-blockers to MVP, and if we argue on that, it should be covered in design/implementation sections.

### 6.1 Rethink about sync replication

The beauty of synchronous replication between the DR HBase clusters mainly is the strong consistency guarantee. If this is provided, clients in CoreApp will not need to make ad hoc decisions about failover when a cluster role transition happens. With that, we can extend to most, if not all, use cases in CoreApp. Moreover, the failover can be mostly transparent to upper level callers with potential observable higher latency for some requests and required retries at Phoenix layer. However, as we discussed above, the overall availability might be not on par with a single clusters’ availability or latency since every write will have to succeed on both clusters before acknowledging to client. Any tail latency issues from either cluster will accrue to the sum of the two. In current HBase 2.x [replication design](https://docs.google.com/document/d/193D3aOxD-muPIZuQfI4Zo3_qg6-Nepeu_kraYJVQkiE), the active falls back to degraded active (DA) state. In DA state, a cluster accepts both read and writes (after replaying remote WALs if any), and it just stops replicating to the other cluster.

### 6.2 Cost effectiveness

So we have two HBase clusters for serving one CoreApp. Does that increase cost? *Yes*. With significantly increased cost, one may argue that increasing overall HBase availability from 99.9% to 99.99% is not worth it. Does it double the cost? *Not necessarily.* There are some ideas to make this DR design more affordable than doubling the cost. The hope is to reduce the overall cost of DR feature from 2X to 1.3~1.5X with similar availability SLA.

* ***A cluster for different failover groups has different roles.*** Basically every CoreApp Cell or use case will be in a failover group, where one of the two HBase clusters is considered “active”. We have can direct HBase traffics to the two HBase clusters evenly if we make one HBase cluster active to half of failover groups and the other HBase cluster active to the other half of failover groups. Failover is operated at failover group level so traffics will be moved to one HBase cluster in a controlled manner. In case of a total cluster failure, we can make the other cluster active for all failover groups, and also scale out the target HBase cluster to serve usual request load. Overall the total number of HBase servers are not necessarily doubled.
* ***Standby cluster being shared by multiple active.*** The idea is one HBase cluster is standby cluster for more than one active HBase clusters. This is limited into one FD since we do not share HBase resource inter-FD. So the potential use case, is the relevant work “[Per user Case in Core Per HBase Cluster](https://salesforce.quip.com/DWXzAwWla7bV#DXaACAgFaPM)”. That way, the same *1* standby cluster is actually running in larger scale than any *N* active clusters. This N:1 mapping seems very affordable without sacrificing overall responsiveness. For this, the inter-cluster replication will be carefully designed so that only standby cluster has all the data for the CoreApp, while all other clusters have only table data for one CoreApp use case. Chances are two use case dedicated active clusters fail at the same time, more load will be directed to the very standby cluster. In this case, we can also explore the aforementioned scaling out (in advance, yes, why not?).
* ***Scaling standby cluster out/down***. Suppose we know the DR cluster is idle most of the time, say 99.9% of time. Can we scale down it to half size regarding DataNode and RegionServer worker nodes? For planned failover, we can scale out to full size upfront. For unplanned failover, scaling out standby cluster to full size can be triggered early than the real failover happens. For example, when we see abnormal client request errors in the active cluster, the standby cluster could be triggered automatically scaled out to increase responsiveness when a cluster role happens potentially. This is a trade-off between cost to serving and the cluster overall availability. Meanwhile, if the active cluster comes back to healthy state for a while, the standby cluster can scale down accordingly.

### 6.3 auto-triggered failover

We ultimately want the failover process to be driven by cluster health. ie failover should happen automatically if the cluster is “unhealthy“.  However we need a reliable way to determine cluster health, since having false positives will be expensive. We should be able to (in theory) use a combination of our cluster health metrics to derive a health signal. Argus metrics driven auto triggered failover will offer more responsiveness. There will be more discussion with Service Maturity team on this. This is considered future work, and will be included in V2 design doc [LINK HERE] of this HBase Failover feature for CoreApp in Falcon. We do not cover design choices for auto-trigged failover in this doc at all.

# Future of Partial Immutability in Phoenix

Phoenix allows our customers to set a table attribute to declare whether a data table (or view) is immutable. Indexes inherit this attribute from their data tables (or views). In the rest of this document, we will continue with our discussion without making a reference to views since they do not add any additional concerns and change to the topic.

By default, tables are mutable. The immutability attribute is actually only used for indexes. Although the Phoenix tables have the immutability attribute, there are no checks in place to prevent overwrites on the immutable tables. Because of the lack of immutability enforcement, the immutable table rows can be overwritten too. Indexes on immutable tables are implemented on the client side and the implementation actually allows overwrites as long as the secondary index key column values are not modified. Please note that detecting if the index columns are modified requires reading the existing data table rows before updating them,  and modifying index columns requires deleting the existing index rows. Handling overwrites of index columns results in costly index maintenance. However, as long as index columns are not modified, even the immutable tables can be overwritten without paying for this costly index maintenance. Some of our customers took advantage of this partially immutable (in other words, partially mutable) indexes and enjoyed the write performance gain due to simpler maintenance of immutable indexes on the client side.

With the introduction of the Phoenix TTL feature, the concept of such partially immutable tables lead to data governance, and correctness issues. Attempting to fix these issues while keeping the implementation of the partially immutable indexes on the client side leads to a great deal of code complexity, and performance issues such that partially immutable indexes become much slower than mutable indexes in terms of write performance.  Thus, this leaves only one choice that is to convert partial immutable tables to mutable tables, as the rest of this document explains.

This document does not imply that purely immutable tables does not work with the Phoenix TTL feature. Purely immutable tables will not have the partial row overwrites causing the issues discussed in this document, and thus will work with the Phoenix TTL feature.  The document shows that if there is a possibility of partially updating a table row after the row has been expired, and the table has one or more global indexes, then the table cannot be labelled as immutable and it needs to be converted to mutable. This conversion does not require any change on the existing content of the table. It is an update on the metadata of the table which is done purely using the ALTER TABLE command, which is existing functionality. It will not cause any service disruption and it can be rolled back in minutes with an EBF schema release should there be any issues.

# Client versus Server Side Operations

In the Phoenix interface, updates to a table are expressed using SQL UPSERT and DELETE statements while in the HBase interface, they are expressed using structures called mutations. 

An HBase table can be viewed as a set of cells where each cell is identified by a key which is composed of a row key, family name, column qualifier and timestamp. The cell holds a value expressed using a byte array. The cell also has some metadata to identify cell type, tag, and sequence id. So essentially, a cell is a key-value structure and HBase is a key-value store. This key value store is a collection of tables which are collections of rows which are collections of cells. A row is identified with a row key and is the set of cells with this row key.  There are mainly two types of cells:  put and delete, and therefore there are two main types of mutations:  put and delete, where a put mutation is a set of put cells and a delete mutation is a set of delete cells.  

The Phoenix client translates the UPSERT and DELETE statements to the corresponding HBase mutations and pass them to the HBase client. Then the HBase client sends these mutations to the HBase region servers that are responsible for holding the rows corresponding to these mutations. If a data table has some indexes, Phoenix updates these indexes along with the data table atomically. For immutable indexes, the index mutations are generated by the Phoenix client and passed to the HBase client. For mutable tables, the index mutations generated by the Phoenix code runs on the HBase region servers.

# Diminishing Value of Client Side Optimization

Why did we have these different code paths for mutable and immutable indexes in the first place? The simple answer is when the indexes were introduced, they were not strongly consistent and generating and applying immutable index mutations was dramatically faster and simpler on the client side. Since indexes were not strongly consistent by design, the client could update the data table and its indexes in parallel without enforcing any order. This parallel update approach resulted in higher write performance.

This write performance gain has been mostly gone with the introduction of strongly consistent indexes since strong consistency requires serializing updates such that indexes are updated first then the data table and finally indexes are updated again to implement a two phase commit protocol. Phoenix still generates immutable index updates on the client side. However, moving immutable index update code to the server side would not make them slower in terms of write performance

# Write Performance Difference 

Why then do immutable indexes still have higher write performance than the mutable indexes do? The reason for this is that for mutable indexes, Phoenix needs to retrieve the existing data table row from disk in order to generate index mutations correctly. Since reading data table is more efficient on the server side and also we need to lock the data table row in order to get consistent read (in the presence of concurrent updates on the same row), mutable indexes are implemented on the server side. If updating an existing index row may result in modifying the column values of the secondary key columns  (i.e., indexed columns) then we also need to delete the existing index row with the old index row key in addition to adding a new row with the new index row key.  Reading the data table row and serializing concurrent updates on the same row using a lock is the main reason why the mutable indexes are slower during data ingestion. The write performance difference between immutable and mutable indexes are about 30%. 

# Phoenix TTL

Phoenix TTL is for purging rows that are expired. A row is expired if it has not been updated for the length of the time specified by the configured TTL value for the table. Phoenix allows users to update the existing rows partially. This means that a row would be composed of cells with different timestamps as the partial updates would only update the timestamps of a subset of cells in a row. Given the cells may have different timestamps, the timestamp of a given row is defined as the maximum of the cell timestamps. However, we do not really need to read all the cells to find out what the row timestamp is. Phoenix makes sure that every row updates whether it is partial or full includes a special internal cell which is not visible to its applications/users. Thus, instead of using reading all cells, Phoenix needs to read this special cell to determine the row timestamp for a given row. To do that the scan on the HBase table is modified to make sure that the special cell is returned by HBase as part of every row scan. Then Phoenix checks the timestamp of this special cell and determines if the row is expired or not. 

A Phoenix background process scans the rows and delete them using the HBase interface if they are expired. This delete operation is logical and it essentially marks the row as deleted instead of physically removing the row from the table. The HBase compaction process looks for these delete rows and physically removes them from their tables. 

# Partial Write Challenge for Phoenix TTL

The partial writes pose a TTL problem for the rows that can be partially updated after they become expired but before they are marked as deleted. We have no control over how the table rows will be used by our customers. And similarly PDS does not have any controls over how their customers would use their own views either. A customer can treat a row as a storage container where the content may expire but the container does not disappear from their application and are reused over time. Thus, partial row updates may result in inclusion of the cells that have been expired. This means that expired row content that should have been deleted will be revived and made visible to the user.  The race between partial updates and the background TTL process determines if these expired cell will be deleted or not. This makes the Phoenix TTL feature nondeterministic. Ideally, row contents that are expired should never be visible again and should be removed from the system. 

To eliminate this nondeterminism, before updating a row partially, Phoenix needs to retrieve the special cell from the row and check if the row has been expired. If the row has been expired, Phoenix needs to delete the existing row before inserting the new version.  As in the case of mutable indexes, since retrieving a row is more efficient on the server side and also Phoenix needs to lock the row in order to get consistent read (in the presence of concurrent updates on the same row), the check for row expiry needs to be done on the server side. This poses a real challenge for implementing a Phoenix TTL feature for immutable tables if we keep updating them on the client side. 

# Demise of Partially Immutable Indexes

Since the immutable tables are not really immutable, they are also subject to the nondeterminism issue. Phoenix needs to check if these rows are expired on the server side before applying the mutations generated by the Phoenix client. Such a check operation on the server side completely washes out the write performance advantage of client side immutable indexes over server side mutable indexes. Actually, it makes them slower than mutable indexes. The reason for this is that TTL check for mutable indexes are needed to be done on the data table only. However, for the client side immutable tables, this check needs to be done on both data and index tables. In addition to the extra checks for row expiration, there is also the consistency issue among these multiple checks. Since the wall clock of a region server may not be in sync with the wall clock of another region server, for one region server the row it checks can be determined as expired while for another region the row with same timestamp can be determined as valid. All these implies that in the presence of partial updates on immutable tables, we cannot have client side immutable indexes with TTL

Now that we know that we cannot have client side immutable indexes with TTL and immutable indexes are not really immutable, there is no intrinsic value for labeling them as immutable anymore. This means that it is better to make them mutable. 

# Upgrading Immutable to Mutable

An immutable data table can be made mutable using the ALTER TABLE command. (Note, currently, due to a bug in Phoenix, this change is not propagated to the index tables. This is not a complex bug to fix). After applying this command, the change will be visible to new Phoenix connections after the client cache is updated. For most of our tables, the client cache is updated immediately when a Phoenix connection is opened.  This means the result of the ALTER TABLE command will be visible to these connections immediately. For other tables, the client cache is updated within an hour or a day. This means immutable tables can be made mutable first and then after waiting for the client cache update, the Phoenix TTL feature can be configured on them. This means we can upgrade immutable tables to mutable tables without service interruption.

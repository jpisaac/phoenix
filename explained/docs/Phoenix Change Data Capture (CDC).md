# Phoenix Native Change Data Capture (CDC) 

Contributors: [Kadir Ozdemir](mailto:kozdemir@salesforce.com), [Viraj Jasani](mailto:vjasani@salesforce.com), [Hari Krishna Dara](mailto:hdara@salesforce.com), [Saurabh Rai](mailto:saurabh.rai@salesforce.com)  
Updated: Aug 3, 2023

This document lays out the CDC design for Phoenix. This design is different from the previous CDC design based on WAL and Kafka such that this design leverages Phoenix Max Lookback and Uncovered Global Indexes. The new design does not require external solutions like Kafka and is simpler to implement.

# Use Cases

The use cases for a Change Data Capture (CDC) feature are centered around capturing changes to a given table (or updatable view) as these changes happen in near real-time. A CDC application can retrieve changes in real-time or with some delay, or even retrieves the same set of changes multiple times. This means the CDC use case can be generalized as time range queries where the time range is typically short such as last x minutes or hours or expressed as a specific time range in the last n days where n is typically less than 7\.

A change can be inserting a new row, updating one or more columns of a table for an existing row, or deleting a row. Phoenix does not currently differentiate inserting a new vs updating an existing row. Similarly, CDC will not differentiate them. It is desirable to provide these changes in the order of their arrival. One can visualize the delivery of these changes through a stream from a Phoenix table to the application that is initiated by the application similar to the delivery of any other Phoenix query results. The difference is that a regular query result includes at most one result row for each row satisfying the query and the deleted rows are not visible to the query result while the CDC stream/result can include multiple result rows for each row and the result includes deleted rows. Some use cases need to also get the pre and/or post image of the row along with a change on the row. 

# High Level Design

The design proposed here leverages Phoenix Max Lookback and Uncovered (Global or Local) Indexes. The max lookback feature retains recent changes to a table, that is, the changes that have been done in the last x days typically. This means that the max lookback feature already captures the changes to a given table. Currently, the max lookback age is configurable at the cluster level. We need to extend this capability to be able to configure the max lookback age at the table level so that each table can have a different max lookback age based on its CDC application requirements.

To deliver the changes in the order of their arrival, we need a time based index. This index should be uncovered as the changes are already retained in the table by the max lookback feature. The arrival time can be defined as the mutation timestamp generated by the server, or a user-specified timestamp (or any other long integer) column. An uncovered index would allow us to efficiently and orderly access to the changes. Changes to an index table are also preserved by the max lookback feature.  
A CDC feature can be composed of the following components:

* **CDCUncoveredIndexRegionScanner**: This is a server side scanner on an uncovered index used for CDC. This can inherit UncoveredIndexRegionScanner. It goes through index table rows using a raw scan to identify data table rows and retrieves these rows using a raw scan. Using the time range, it forms a JSON blob to represent changes to the row including pre and/or post row images.  
* **CDC Query Compiler**: This is a client side component. It prepares the scan object based on the given CDC query statement.   
* **CDC DDL Compiler**: This is a client side component. It creates the time based uncovered (global/local) index based on the given CDC DDL statement and a virtual table of CDC type. CDC will be a new table type. 

Consider the following table with two PK columns and 4 non PK columns. Let us call this table MyTable

| PK1 | PK2 | A | B | C | D |
| :---- | :---- | :---- | :---- | :---- | :---- |
|  |  |  |  |  |  |

A CDC DDL syntax can be as follows: 

**Create CDC** \<CDC Table Name\> **on** \<Data Table Name\> **INCLUDE** (pre | post | change | latest)  **SALT\_BUCKETS**\=\<salt bucket count\>

The above CDC DDL creates a virtual CDC table and an uncovered index. The CDC table PK columns start with the timestamp or user defined column and continue with the data table PK columns. The CDC table includes one non-PK column which is a JSON column. The change is expressed in this JSON column in multiple ways based on the CDC DDL or query statement. The change can be expressed as just the mutation for the change, the latest image of the row, the pre image of the row (the image before the change), the post image, or any combination of these. The CDC table is not a physical table on disk. It is just a virtual table to be used in a CDC query. Phoenix stores just the metadata for this virtual table.   
Create CDC MyCDC on MyTable INCLUDE (pre, all)

The above CDC DDL creates the following logical table called MyCDC and an uncovered global index. The changes are retained for 3 days if the max lookback age is 3 days.

| PHOENIX\_ROW\_TIMESTAMP() | PK1 | PK2 | CDC JSON |
| :---- | :---- | :---- | :---- |
|  |  |  |  |

The client can retrieve the changes using the following SQL select statement: 

Select \* from MyCDC where PHOENIX\_ROW\_TIMESTAMP() \>= TO\_DATE( …) AND PHOENIX\_ROW\_TIMESTAMP() \< TO\_DATE( …)

This query would return the rows of the CDC table which is constructed on the server side by CDCUncoveredIndexRegionScanner by joining the uncovered index row versions with the corresponding data table row version (using raw scans). The above select query can be hinted at by using a new CDC hint to return just the actual change, pre, pos, or latest image of the row, or a combination of them to overwrite the default JSON column format defined by the CDC DDL statement. 

The CDC application will run the above query in a loop. When the difference between the current time of the application and the upper limit of the time range of the query becomes less than s milliseconds, say x milliseconds, then the application thread needs to sleep s \- x milliseconds. The value for s can be small such as 1000 milliseconds. This is to make sure that time skew among the server wall clocks does not lead to data loss.  

## Hot Spotting

A global time based index may create hot spotting during writes. This is because the same region of the global index will keep getting updated. Since the global index would be uncovered, the size of the updates will be usually smaller than the data table updates. If we assume that index mutations are n times smaller than data table mutations, then a single index region will be able to sustain writes from n data table regions if the data table does not have any other indexes. When the data table has other indexes, the data table write can slow down by 3 times or so. This allows a single index region to match with 3n data table regions.

If the number of active data table regions is more than a single index region can sustain then we need to distribute the load to multiple index regions using salting. When the index is salted, the Phoenix client merges and sorts the results from index regions to provide orderly delivery. This is already supported by the Phoenix client and done by the result iterator created by the CDC compiler.

A local time based index does not have the hot spotting issue but can result in slower CDC queries for tables with a large number of regions. That is why this proposal suggests using global indexes by default.

# Non-Functional Requirements

## Performance

The throughput of a CDC query from using a single thread on a table should match with the write throughput of the table using a single thread.

## Scalability

The CDC query throughput should scale to the write throughput. The number of threads used to scale the write throughput should be less than or equal to the number of CDC queries each from a different Phoenix client instance.

## Availability

The CDC write or query operation should not impact the availability of a table.

# Low Level Design

### New Grammar PhoenixSQL.g

#### Create CDC

create\_cdc\_node returns \[CreateCDCStatement ret\]  
   :    CREATE CDC (IF NOT ex=EXISTS)? o=cdc\_name ON t=from\_table\_name  
        LPAREN (tcol=column\_name | tfunc=cdc\_time\_func) RPAREN  
        (INCLUDE LPAREN v=cdc\_change\_scopes RPAREN\`)?  
        (p=fam\_properties)?  
   ;

cdc\_name returns \[NamedNode ret\]  
    :   name=identifier {$ret \= factory.cdcName(name); }  
    ;

cdc\_time\_func returns \[FunctionParseNode ret\]  
    :   field=identifier LPAREN l=zero\_or\_more\_expressions RPAREN  
   ;

cdc\_change\_scopes returns \[Set\<CDCChangeScope\> ret\]  
    :   v=cdc\_change\_scope ( COMMA v=cdc\_change\_scope )\*  
    ;

cdc\_change\_scope returns \[CDCChangeScope ret\]  
    :   v=(PRE | POST | LATEST | ALL)  
    ;

#### Drop CDC

drop\_cdc\_node returns \[DropCDCStatement ret\]  
   : DROP CDC (IF ex=EXISTS)? o=cdc\_name ON t=from\_table\_name  
   ;

#### Alter CDC

alter\_cdc\_node returns \[AlterIndexStatement ret\]  
   : ALTER CDC (IF ex=EXISTS)? o=cdc\_name ON t=from\_table\_name  
     (SET?) p=fam\_properties)?  
   ;

## CDC Query e2e Flow \- 

### **Approach 1: Leveraging the Current Uncovered Index Scan Flow (Recommended)**

**Phoenix Client \-** 

1. Simultaneously initiate scans across multiple region servers based on the query range and the corresponding uncovered index table regions  
2. Enhance the scanning process by embedding relevant metadata key-value attributes within the Hbase Scan object, facilitating interaction with the CDCUncoveredIndexRegionScanner coprocessor.

**Phoenix Server/Coprocessor \-** 

1. Conduct a raw scan of the Uncovered index table concurrently across different region servers. This process is executed within the specified query ranges.  
2. Organize all rows of the index table for each row key of the Datatable, followed by a skip scan of the Datatable using skip scan filter. Retrieve all versions within the time range of the rows available in the index table. (Assumption: Rows for a specific Datatable row key in the index table are chronologically consecutive.)  
3. Formulate a structured JSON response encompassing all updates and subsequently return it.

**Potential problem \-**   
Some rows for the updates of a particular data table row key can be in different region servers of the index table. When we create JSON for each update per region server and return the response, All other change scope should work fine except the LATEST change scope. We might have to write a separate merging logic at the client side to address this issue.

### **Approach 2: Client-Side Uncovered Index Scanning and Data Table Querying**

**Phoenix Client \-** 

1. Initiate parallel scans across multiple region servers, aligning each scan with the query range and the uncovered index table regions.  
2. Include pertinent metadata key-value attributes in the Hbase Scan object, effectively engaging the CDCUncoveredIndexRegionScanner coprocessor.

**Phoenix Server/Coprocessor \-** 

1. Conduct raw scans of the Uncovered index table concurrently across different region servers. Subsequently, return the response obtained from these scans.

**Phoenix Client \-** 

1. On the client side, consolidate and merge the responses retrieved from the uncovered index table scans.  
2. Create a distinct query to scan the data table based on the merged results from the uncovered index table responses.

**Phoenix Server/Coprocessor \-** 

1. Conduct a raw scan of the data table  
2. Generate a structured JSON response encapsulating all updates and proceed to return it.

**Approach 3: Leveraging the Current Uncovered Index Scan Flow With Client Side JSON Generation**

**Phoenix Client \-** 

1. Simultaneously initiate scans across multiple region servers based on the query range and the corresponding uncovered index table regions  
2. Enhance the scanning process by embedding relevant metadata key-value attributes within the Hbase Scan object, facilitating interaction with the CDCUncoveredIndexRegionScanner coprocessor.

**Phoenix Server/Coprocessor \-** 

1. Conduct a raw scan of the Uncovered index table concurrently across different region servers. This process is executed within the specified query ranges.  
2. Organize all rows of the index table for each row key of the Datatable, followed by a skip scan of the Datatable using skip scan filter. Retrieve all versions within the time range of the rows available in the index table. Return the response. (Assumption: Rows for a specific Datatable row key in the index table are chronologically consecutive.)

**Phoenix Client \-** 

1. Generate a structured JSON response encapsulating all updates at the client side.

## Comparison with other DB Implementations 

1. DynamoDB always includes the full row, not just the columns that changed. ([link](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Streams.html))  
   1. **StreamViewType** \-   
   2. **Key attributes only** — Only the key attributes of the modified item.  
   3. **New image** — The entire item, as it appears after it was modified.  
   4. **Old image** — The entire item, as it appeared before it was modified.  
   5. **New and old images** — Both the new and the old images of the item.  
2. PostgreSQL ([link](https://medium.com/@ramesh.esl/change-data-capture-cdc-in-postgresql-7dee2d467d1b))  
3. ScyllaDB ([link](https://opensource.docs.scylladb.com/stable/using-scylla/cdc/index.html))  
   1. There are different types of entries appearing in the CDC log:  
      1. delta entries, which describe “what has changed”,  
      2. pre-image entries, which describe “what was before”,  
      3. and post-image entries, which describe “the end result”.  
4. Cockroach DB ([link](https://www.cockroachlabs.com/docs/stable/changefeed-messages))  
   1. **Key**: An array composed of the row's `PRIMARY KEY` field(s) (e.g., `[1]` for JSON or `{"id":{"long":1}}` for Avro).  
   2. **Value**:  
      1. One of four possible top-level fields:  
         1. `after`, which contains the state of the row after the update (or `null` for `DELETE`s).  
         2. `updated`, which contains the [updated](https://www.cockroachlabs.com/docs/v23.1/create-changefeed#updated-option) timestamp.  
         3. `resolved`, which is emitted for records representing [resolved](https://www.cockroachlabs.com/docs/stable/changefeed-messages#resolved-messages) timestamps. These records do not include an `after` value since they only function as checkpoints.  
         4. `before`, which contains the state of the row before an update. Changefeeds must use the [`diff` option](https://www.cockroachlabs.com/docs/v23.1/create-changefeed#diff-opt) with the default [`wrapped` envelope](https://www.cockroachlabs.com/docs/stable/changefeed-messages#wrapped) to emit the `before` field. When a row did not previously have any data, the `before` field will emit `null`.  
         5. For [`INSERT`](https://www.cockroachlabs.com/docs/v23.1/insert) and [`UPDATE`](https://www.cockroachlabs.com/docs/v23.1/update), the current state of the row inserted or updated.  
         6. For [`DELETE`](https://www.cockroachlabs.com/docs/v23.1/delete), `null`.
